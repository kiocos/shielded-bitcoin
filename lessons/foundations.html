Read a Bitcoin payment.

Bitcoin records which outputs are spent and which new outputs are created. The amounts are public.

You’ll be able to: Read a small Bitcoin transaction and separate public facts from ownership guesses.

A balance is a collection of outputs

A UTXO is an unspent transaction output: an amount of bitcoin with conditions for spending it. An ordinary payment consumes entire UTXOs and creates new outputs. The old output does not remain partly spent.

An input identifies an earlier output using its transaction identifier and output number. A signature commonly supplies spending authorization. The output’s spending conditions determine exactly what is required.

Payment, change and fee

Suppose Alice spends a 12,000-sat output. She creates 7,000 sats for Bob and 4,700 sats in change. The remaining 300 sats are the Bitcoin fee. Change is an ordinary output back to Alice; the blockchain does not label it “change.”

12,000 = 7,000 + 4,700 + 300

An observer sees amounts, output scripts and links to earlier outputs. “That output belongs to Alice” requires additional information. Address clustering is an inference, not a name field written into every transaction.

Where Shielded Bitcoin changes the picture

A carrier transaction is still an ordinary Bitcoin transaction with visible funding and fees. It also publishes a shielded envelope. The private transfer inside that envelope has its own notes and validation rules. Its amounts balance exactly; its Bitcoin publication fee is paid outside the shielded balance.

A Bitcoin confirmation establishes inclusion in the chain. It does not establish that the envelope passes shielded replay.

M02 · Core course · about 8 minutes

Give each cryptographic tool one job.

Hiding information, binding information and proving a rule are different tasks.

You’ll be able to: Choose the right primitive for hiding data, committing to data, authorizing a spend, or proving a condition.

Hashing and commitments

A hash function turns bytes into a fixed-size result. A cryptographic hash is designed to make it hard to find distinct inputs with the same result or recover a suitable input from a result. It is not encryption: there is no decryption key.

A bare hash does not necessarily hide its input. If the input is one of ten possible amounts, an observer can hash all ten and compare. A commitment binds someone to a value; a hiding commitment also conceals that value, usually using randomness. Binding and hiding are separate properties.

Encryption, signatures and proofs

Encryption
Protects a message so the intended key holder can recover it. The encrypted bytes are called ciphertext.
Digital signature
Lets someone verify authorization of a message using a public key. It does not conceal the message.
Zero-knowledge proof
Establishes a defined claim without disclosing the private evidence beyond what the public claim implies.

The same transfer uses several tools

Recipient ciphertexts carry private notes. Hashes bind envelope fields and tree structure. The proof connects private notes to public nullifiers, ciphertexts and a root. A Bitcoin signature authorizes the carrier’s spend.

None replaces all the others. An encrypted note can contain an invalid amount. A valid signature can authorize publication of an invalid envelope. Each verifier must check the rule that concerns it.

Checking an answer and finding one are different jobs.

P versus NP asks whether every efficiently checkable “yes” answer can also be found efficiently.

Our previous question was “Does some selection total 31?” It has a yes-or-no answer. Such questions are called decision problems. Complexity theory studies how the work grows across larger inputs, not just whether this small example feels difficult.

P

Problems for which an algorithm can determine the yes-or-no answer efficiently.

NP

Problems whose “yes” answers have witnesses of manageable size that an algorithm can check efficiently.

Here, “efficiently” means polynomial time: the work has a bound such as input length squared or cubed. The witness length must also have a polynomial bound. This is a mathematical growth condition, not a promise of a fast app.

NP means nondeterministic polynomial time. It does not mean “non-polynomial.” Every problem in P is also in NP. Some NP problems are easy to solve.

Cook, definitions, pp. 1–3.

What remains unknown?

P = NP? Does an efficient way to check witnesses always imply an efficient way to decide whether a valid witness exists? Nobody has proved the answer. The enormous number of possible selections alone does not settle it. Clay Mathematics Institute: unsolved.

And “NP-complete”?

An NP-complete problem is in NP and can express every other NP problem through an efficient translation. An efficient general algorithm for any one NP-complete problem would imply P = NP. This describes a whole family of inputs; a particular small instance can be easy.

Cook, §2.

Check the claim without receiving the private evidence.

Zero knowledge is a privacy property of a proof system.

The prover makes the proof. The verifier checks it. A zero-knowledge protocol lets the verifier learn that the claim holds without learning anything extra from the proof beyond what the public information and the claim’s truth already imply.

Justin Thaler, §11.1: what zero knowledge means.

Three requirements work together

Completeness
An honest prover with valid evidence can make the verifier accept.
Soundness
A cheating prover should not get a false claim accepted, except with a suitably tiny probability. For the arguments we use here, this depends on limits on the attacker’s computation and on cryptographic assumptions.
Zero knowledge
The proof adds no disclosure beyond the public claim. This is a separate requirement from rejecting false claims.

Thaler §§3.1–3.2 and 11.1.

“Zero” does not mean the verifier knows nothing. A Shielded Bitcoin envelope still exposes public nullifiers, ciphertexts, input/output counts and an anchor. Its carrier transaction also exposes timing and fee-funding data. Observers can combine public information with outside knowledge.

Shielded Bitcoin §20.

Where does encryption fit?

Encryption lets a recipient recover the note’s contents with the right key. The transfer proof lets indexers check the transfer’s rules without recovering those contents. Encrypting a made-up amount would hide it, but would not establish that it came from valid inputs.

The proof must also establish that the encrypted outputs match the notes used in its checks. Otherwise someone could prove one payment while publishing something different.

Shielded Bitcoin §14 and Appendix B.

How can a proof be convincing without disclosing the witness?

The prover does not send the private values for the verifier to check directly. A cryptographic construction produces messages that satisfy verification equations when the hidden values obey the rules. The construction must provide both resistance to cheating and the privacy property. Simply hiding some fields is insufficient.

A formal zero-knowledge analysis asks whether the verifier’s view could be simulated without the private witness. If it could, that view cannot provide extra evidence about the witness. This is a security argument about the protocol; it does not give ordinary users a way to forge proofs.

Thaler §11.1; Groth’s concrete construction.

What does a SNARK promise?

A short proof that is quick to check, with no back-and-forth during proof verification.

SNARK means Succinct Non-interactive Argument of Knowledge. Read the words as different properties:

S · Succinct
The proof is short and verification is cheap relative to checking the full computation. Creating the proof can still take substantial work; the verifier must also process the public inputs.
N · Non-interactive
The prover sends one proof instead of answering a sequence of verifier challenges. The parties still need agreed parameters and rules.
AR · Argument
Resistance to cheating depends on limits on the attacker’s computation and on the construction’s cryptographic assumptions.
K · Knowledge
The proof establishes that the prover has a valid witness, rather than merely asserting that one exists. This does not identify the person using the wallet.

A zk-SNARK also provides zero knowledge. “SNARK” alone does not promise privacy. Zero knowledge alone does not promise a short, non-interactive proof.

Groth: succinct non-interactive arguments; Thaler §7.4: knowledge soundness.

How do payment rules become something provable?

A circuit expresses a computation as small operations and checks. A constraint is a condition the values must satisfy. For a transfer, one condition is “input value equals output value.” Others establish ownership, tree membership and correct encryption.

What happens between “prove” and “verify”?

In Groth16, the circuit’s checks are translated into polynomial relations. Setup produces parameters for that circuit. The prover uses those parameters, the witness and fresh randomness to produce three mathematical objects called group elements. The verifier checks a pairing equation involving the proof, public inputs and verification key.

You do not need to calculate pairings to explain the architecture. The essential point is that the verifier checks a cryptographic relationship tied to all the circuit’s rules. It does not receive the hidden values or rerun every private operation.

The formal “knowledge” requirement uses an extractor: an algorithm that could recover a valid witness given special access to a successful prover’s computation. An ordinary verifier does not have that access. This is not a way to recover private notes from a published proof; copying such a proof also does not establish ownership of those notes.

Two checks prevent two different attacks

Repeat the same marker: replay finds it in the accepted nullifier set and rejects the new envelope. It also rejects repeated markers within one envelope.

Observers can detect a repeated marker without knowing which leaf produced it. The sender of a note cannot calculate the recipient’s marker from the sent plaintext alone; the recipient’s nullifier secret is needed.

The position distinguishes notes at different canonical positions. Following a chain reorganization, wallets must use the positions and spent state obtained from the surviving history, not stale local records.

Inputs, outputs and the connecting rules

For inputs, the proof checks membership under the anchor root, the spender’s authority and the required nullifier derivation. For outputs, it checks that the ciphertexts encrypt the notes described in the witness.

What stays private and what is public

The witness contains note plaintexts, spending secrets and membership paths. Public inputs include the anchor root, nullifiers, relevant output data and the body binding. The exact logical tuple and encoding are specified by the circuit and profile.

A proof checks the defined constraints. If the circuit forgot an essential rule, a mathematically valid proof would not add that missing rule. This is why the statement itself must be examined, not just the proof system’s name.

What replay must still check

Replay selects the root for the anchor height, checks that the height is allowed, checks public nullifier uniqueness and verifies the proof under the correct key. It also parses the envelope and recomputes its binding hash.

A valid proof does not establish that the current accepted nullifier set is empty for those inputs. That is a separate replay check. Nor does a valid private transfer prove that a complete BTC withdrawal mechanism exists.

    Your goal: explain witness encryption, then distinguish key release from a covenant.

    Start with the condition

    A covenant constrains how a coin may be spent—for example, by restricting the next transaction’s outputs. PIPEs v2 instead provides conditional release of a signing key. Once recovered, that key can sign arbitrary transactions; the paper explicitly disclaims persistent, per-signature covenant enforcement. §1.1

    What “witness encryption” means

    A statement defines a checkable condition. A witness is data satisfying it. WE encrypts a message under the statement; a valid witness enables decryption. PIPEs needs an extractable-security assumption: learning the protected message requires knowledge of a witness. §2.5

    An actual condition · a toy demonstration

    “Know two integers greater than 1 whose product is 77.”

    Try 3, 11, then 7, 11. The pair is a witness. The number 77 alone is not.

    The demo signing key has not been released.

    This only illustrates the witness relation. It is not encryption, a secure factoring example, or a PIPE implementation. Real WE must protect the message even if an attacker rewrites the decryption software.

    Vocabulary

    UTXO
    An unspent Bitcoin transaction output: an amount with conditions that a spending transaction must satisfy.
    Arity
    The numbers of consumed input notes and created output notes. These counts are public.
    Note
    Private value record (v, d, rseed). Its plaintext is encrypted; the tree stores a public derived leaf.
    Leaf / tree / root
    A leaf hashes public output data and binding fields. One append-only tree collects accepted output leaves. A root commits to the tree at a checkpoint. Spent leaves stay.
    Nullifier
    H_nf(sk_nf, ρ, pos): the note’s public spend marker. The proof fixes its derivation; replay rejects a repeated marker.
    Anchor
    A prior block height selecting a replayed tree root for input membership. Current nullifiers still determine whether inputs were already spent.
    Witness / ZK proof
    A witness is data satisfying a condition; it is not inherently private. A zero-knowledge proof lets a verifier check the claim without receiving its private witness.
    Envelope / carrier
    The envelope contains shielded transfer data. The carrier is the Bitcoin transaction publishing it and paying the Bitcoin fee.

    Shielded Bitcoin §§3, 8, 9 and 14.

    Boundary vocabulary

    Covenant
    A restriction on how a coin may be spent, such as constraints on the next transaction’s outputs.
    Witness encryption (WE)
    Encryption under a statement; a satisfying witness enables message recovery.
    PIPEs v2
    Uses WE to release a Bitcoin signing key conditionally. Once released, that ordinary key can sign arbitrary messages.
    SNARK / AADP
    A SNARK gives a short, non-interactive argument of knowledge; zero knowledge is an additional property. The proposed AADP WE construction encodes verification through an arithmetic matrix construction; its large ciphertext is separate from the proof.

    PIPEs §§1.1, 2.5 and 4; AADP introduction.

    Wallet capabilities

    Spending secret
    Supplies spending authority and derives incoming and nullifier capabilities.
    Nullifier secret
    Derives a note’s marker with the required note data and canonical position. It cannot authorize a spend alone and is excluded from the disclosure modes.
    Incoming viewing / outgoing recovery
    Read-only access to received outputs / sent-output recovery records. Neither alone identifies the consumed input notes or proves a complete current balance.

    Shielded Bitcoin §§6–7.

    Anchor and recovery checks

    In block H, the example profile allows anchors from H − 100 through H − 1. The current nullifier set still applies. A wallet can require additional confirmations. After a reorganization, synchronize positions, roots and spent status with the active history.

    Recovery needs the seed, relevant history, accepted positions and spent-state checks. Decrypting a record does not establish that its envelope was accepted. Activation notes may need deployment-defined bootstrap recovery data.

    Shielded Bitcoin §§15–16 and Appendix A.6.

    The words behind the proof.

    Plain-English definitions for reading the Shielded Bitcoin and PIPEs papers.

    Statement
    A precise claim about public information.
    Witness
    Data that satisfies the claim’s checking rule. It is not inherently private.
    Relation
    The rule for checking a public input together with a proposed witness.
    NP statement
    A claim with a witness of polynomially bounded length that can be checked in polynomial time.
    P / NP
    P: efficiently decidable yes-or-no problems. NP: yes-instances have efficiently checkable witnesses. P is contained in NP; whether they are equal remains open.
    Proof
    Evidence sent to a verifier. In a zk-SNARK, this is a separate object generated using the private witness.
    Prover / verifier
    The party producing a proof / the party checking it.
    Zero knowledge
    The proof discloses nothing extra beyond what the public information and claim’s truth imply.
    SNARK
    Succinct Non-interactive Argument of Knowledge. Short proof, cheap verification, no proof-time dialogue, computational security, and a knowledge requirement.
    zk-SNARK
    A SNARK that also has the zero-knowledge privacy property.
    Circuit / constraint
    A computation expressed as small operations / a condition its values must satisfy.
    Groth16
    The proof system used by the Shielded Bitcoin example profile; it needs circuit-specific trusted setup.
    Witness encryption
    Encryption under a statement, with decryption enabled by a satisfying witness.

    Definitions: Cook §§1–2; Thaler §§3, 7.4, 11.1; Groth; PIPEs §2.5.

    Four questions to ask about any proof

    1. What exact claim is being proved?
    2. What evidence does the prover use?
    3. What does the verifier see and check?
    4. What assumptions and additional protocol checks are needed?

    A presentation sentence

    “The wallet proves that it knows private notes it can spend and that the new transfer obeys the rules. Indexers check that proof and the public replay rules. Bitcoin supplies publication and order.”

    Shielded Bitcoin §§14–15.
