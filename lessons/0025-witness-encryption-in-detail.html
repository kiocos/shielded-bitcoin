Encrypt for a condition instead of a named recipient.

Witness encryption uses a statement for encryption and satisfying evidence for decryption.

You’ll be able to: Explain how a condition can control decryption without confusing WE with ordinary note encryption.

Name the three objects

The message is what you want to keep secret. The statement describes a condition. The witness is data that passes that condition’s check.

The encryption algorithm takes the public statement and message. The decryption algorithm uses a satisfying witness to recover the message. The encryptor need not have the witness in order to encrypt.

Encrypt(statement, message) → ciphertext
Decrypt(ciphertext, satisfying witness) → message

An example of the interface

Use the earlier statement “some selection from 3, 6, 11, 15, 22, 29 totals 31.” The selection 3, 6, 22 is a witness. In a WE construction for that relation, it would enable recovery of the encrypted message.

This tiny example is easy to solve, so it supplies no useful secrecy. It explains the interface. A browser that runs an if-statement and then displays a hidden string is not implementing witness encryption: anyone can inspect its code.

A proof can itself be the witness

Suppose the chosen condition is “this SNARK proof verifies for these public inputs and this verification key.” The witness for that condition is the proof. It is a different object from the private witness used to produce the proof.

Anyone possessing a qualifying WE witness can use it. Decryption does not depend on the name of the person who found it. If an application publishes the qualifying proof, its design must account for others being able to use it.

The security assumption matters

PIPEs requires an extractable-security form of WE: roughly, learning protected message information should require possessing the necessary witness. Basic WE definitions and stronger guarantees should not be treated as interchangeable.

The candidate construction in these papers is a research proposal with heuristic security and high modeled costs. The conceptual interface is much simpler than a practical implementation.
