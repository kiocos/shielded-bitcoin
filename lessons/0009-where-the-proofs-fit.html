Follow the proof to the component that uses it.

Shielded transfer validation and proposed Bitcoin key release are separate uses of proofs.

1. A private transfer

  1. The wallet has a witness

    Private notes, secrets and tree paths. It constructs payment outputs and their ciphertexts.

  2. The wallet produces a transfer zk-SNARK

    The proof establishes membership, spending authority, correct nullifiers, correct output encryption, amount ranges and exact balance. It is bound to the transfer body.

  3. A Bitcoin transaction publishes the envelope

    Bitcoin establishes publication and order. Its consensus rules do not validate the shielded transfer proof.

  4. Indexers replay and check the envelope

    They check the proof and separate rules such as whether the anchor is allowed and whether nullifiers were already used. Only an accepted envelope changes shielded state.

Shielded Bitcoin §§14–15 and Appendix A.7.

What does “state” contain?

Accepted output leaves accumulate in one logical note tree per protocol instance. The accepted nullifier set records spent inputs. Root history records the tree after each block. Spent leaves stay in the tree.

Indexers using the same completed profile, starting state and Bitcoin history reconstruct equivalent copies. They do not assign different users’ notes to private indexer-specific trees. An indexer can track other protocol instances, but those are separate states, not partitions of this shared tree.

Shielded Bitcoin §§8 and 15 · Try the tree exercise.

2. Proposed control of a Bitcoin signing key

Witness encryption (WE) encrypts a message under a statement. Data satisfying that statement enables decryption. In PIPEs, the encrypted message is a Bitcoin signing key.

  1. A condition is chosen

    For example, a proposed application could require evidence of an authorized withdrawal. A complete application must specify exactly what that means.

  2. A proof can become the WE witness

    The WE condition can be “this SNARK verifier accepts this proof for these public inputs.” The proof itself then supplies evidence for that new condition.

  3. Decryption releases the signing key

    The holder can make an ordinary Bitcoin signature. Bitcoin checks that signature and its normal transaction rules.

The same word can describe different data: the transfer SNARK’s witness contains private note data; a WE witness can be a SNARK proof. A witness is whatever satisfies the particular check.

A covenant restricts how a coin can be spent, for example by constraining transaction outputs. Releasing an ordinary signing key does not itself preserve such a restriction: the recovered key can sign arbitrary messages. PIPEs explicitly identifies this limitation.

PIPEs v2 §§1.1, 2.5, 4 and 5.3.

The Shielded Bitcoin transfer paper does not specify the complete BTC entry/exit mechanism. A valid transfer proof is not automatically a withdrawal authorization. Anyone holding a qualifying WE witness can use it to decrypt, so a complete application must account for who can obtain that evidence. PIPE setup also uses a separate proof that the encrypted key matches the public signing key.

Why can a short proof require enormous WE data?

The proof and the WE ciphertext are different objects. In the candidate AADP construction, the ciphertext’s size depends on encoding the computation that checks the witness. A small SNARK proof can still require a costly verifier to encode.

The papers model a ciphertext around 338 TB for selected parameters. That is a research estimate for the candidate WE construction, not the size of every shielded transfer. Making the verifier cheaper and making its representation smaller are different goals from shortening a transfer proof.
